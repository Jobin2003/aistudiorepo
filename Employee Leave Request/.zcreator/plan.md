A role-based employee leave app that routes requests to each employee’s assigned manager, records approval or rejection, requires HR to confirm balance deductions, notifies employees, and displays completed approved leave on a Creator calendar.

## User Profiles

Establish separate Employee, Manager, and HR user profiles so each group receives the correct experience and access level.

Create shell custom profile files only, with name and type and no ModulePermissions yet: Employee (Predefined:false; intended to submit and view own requests and balances), Manager (Predefined:false; intended to review assigned employees’ requests and view team leave), and HR (Predefined:false; intended to manage employee records, leave types, balances, and complete approved requests). Do not create Administrator or other default profiles. Do not create roles.

## Employees

Maintain the employee directory and each employee’s assigned manager, which drives automatic approval routing.

Create form Employees. Fields: Details section (section); Employee_ID (autonumber, start index 1001); Employee_Name (name, first and last name enabled and mandatory as supported); Work_Email (email, must have, unique, personal data); Department (picklist with Human Resources, Finance, Sales, Marketing, Operations, Engineering, Customer Support, Other; must have); Job_Title (text, must have); Manager (lookup to Employees.ID, display Employee_Name, optional to allow top-level managers); Employment_Status (picklist Active, Inactive; must have, initial Active); Hire_Date (date, must have). Reports: default list All_Employees showing ID, name, email, department, title, manager, status, and hire date; HR access, Manager read access, Employee no access. Workflows: on validate for add/edit, prevent an employee from being selected as their own manager; otherwise rely on declarative mandatory/unique/default properties. No roles, permissions blocks, or device mappings in this segment.

## Leave_Types

Define the leave categories employees can request and whether weekends are included in duration calculations.

Create form Leave_Types. Fields: Details section (section); Leave_Type_Name (text, must have, unique); Description (textarea); Default_Annual_Allocation (decimal, must have, 2 decimal places, nonnegative validation); Count_Weekends (checkbox, initial false); Active (checkbox, initial true). Reports: default list All_Leave_Types showing name, description, default allocation, weekend rule, and active status; HR access only. Workflows: on validate rejects negative Default_Annual_Allocation. No permissions blocks or device mappings in this segment.

## Leave_Balances

Track each employee’s allocation, usage, and remaining entitlement separately for every leave category.

Create form Leave_Balances. Fields: Balance Details section (section); Employee (lookup Employees.ID, display Employee_Name, must have); Leave_Type (lookup Leave_Types.ID, display Leave_Type_Name, must have); Balance_Year (number, must have, initial current year where declaratively supported); Opening_Allocation (decimal, must have, 2 decimal places, nonnegative); Used_Days (decimal, must have, 2 decimal places, initial 0, nonnegative); Remaining_Days (formula decimal equivalent = Opening_Allocation - Used_Days, visible). Reports: default list All_Leave_Balances showing employee, leave type, year, allocation, used, remaining; HR full access. List My_Leave_Balances filtered to logged-in employee via Employees.Work_Email and current user's email, showing leave type, year, allocation, used, remaining; Employee read access. List Team_Leave_Balances filtered to employees whose Manager corresponds to logged-in manager, Manager read access. Workflows: on validate ensures Opening_Allocation and Used_Days are nonnegative and Used_Days does not exceed Opening_Allocation; on add/edit validation prevents duplicate Employee + Leave_Type + Balance_Year combinations. No permissions blocks or device mappings in this segment.

## Leave_Requests

Run the complete request lifecycle from employee submission through manager review, HR balance confirmation, notifications, and calendar visibility.

Create form Leave_Requests with blueprint-enabled Status lifecycle. Fields: Request Details section (section); Request_Number (autonumber, start index 10001); Employee (lookup Employees.ID, display Employee_Name, must have); Leave_Type (lookup Leave_Types.ID, display Leave_Type_Name, must have); Start_Date (date, must have); End_Date (date, must have); Requested_Days (decimal, must have, 2 decimal places, read-only to users through profile permissions and computed by workflows); Reason (textarea, must have); Supporting_Document (upload file, optional); Approval Details section (section, visibility true); Assigned_Manager (lookup Employees.ID, display Employee_Name; populated automatically); Status (picklist Submitted, Pending HR, Completed, Rejected; initial Submitted; blueprint stage field); Manager_Comments (textarea); Manager_Action_Date (datetime); HR_Comments (textarea); HR_Processed_By (email); HR_Processed_Date (datetime); Balance_Before (decimal, 2 places); Balance_After (decimal, 2 places). Form record owner should use Added_User. Reports: default list All_Leave_Requests for HR showing all request and audit fields; list My_Leave_Requests filtered to logged-in employee, showing request number, type, dates, days, status, and relevant comments; list Manager_Review_Queue filtered to Assigned_Manager.Work_Email == zoho.loginuser and Status == Submitted; list HR_Processing_Queue filtered Status == Pending HR; kanban Leave_Request_Board grouped by Status for HR; calendar Approved_Leave_Calendar filtered Status == Completed with employee as display field and Start_Date/End_Date. Blueprint: start stage Submitted. Transition Approve by Manager profile from Submitted to Pending HR, requiring optional Manager_Comments, stamping Manager_Action_Date and notifying employee of manager approval/pending HR. Transition Reject by Manager profile from Submitted to Rejected, requiring Manager_Comments, stamping date, and notifying employee of rejection. Transition Confirm_Balance_Update by HR profile from Pending HR to Completed: fetch matching Leave_Balances for employee/type/year, verify sufficient Remaining_Days, store before/after values, increment Used_Days by Requested_Days, stamp HR processor/date/comments, and notify employee that approval is complete; completed record then appears on Creator calendar. Include audit entries for submission and every transition by inserting into Audit_Log. Form workflows: on load default Employee by matching zoho.loginuser, lock employee/manager/status/calculated and audit fields as appropriate, and initialize visibility; on user input of Employee populate Assigned_Manager; on user input of Leave_Type, Start_Date, and End_Date recompute Requested_Days according to Count_Weekends (inclusive dates, excluding weekends when configured); on validate enforce End_Date >= Start_Date, active employee/type, assigned manager exists, positive duration, matching balance for the start year, same-year request, and sufficient remaining balance at submission; on success notify assigned manager of new submission. Profile-sensitive actions and fields are finalized in Permissions. No device mappings in this segment.

## Audit_Log

Keep a read-only history of submissions, approvals, rejections, and HR balance updates for accountability.

Create form Audit_Log. Fields: Audit Details section (section); Event_Time (datetime, must have); Actor_Email (email, must have); Action (picklist Submitted, Manager Approved, Manager Rejected, HR Completed, Balance Updated; must have); Leave_Request (lookup Leave_Requests.ID, display Request_Number, must have); Previous_Status (text); New_Status (text); Details (textarea). Reports: default list Leave_Audit_Log showing event time, actor, action, request, prior/new status, and details, sorted newest first; HR access only. Records are created only by Leave_Requests workflows/blueprint transitions; users receive no create/edit/delete UI permission. No workflows, permissions blocks, or device mappings in this segment.

## Leave_Dashboard

Provide a polished overview of leave activity with role-relevant totals, status trends, upcoming absences, and quick links.

Create page Leave_Dashboard using a primary .dshtml snippet styled with ZCS components and Creator theme variables. Include KPI cards for submitted requests, pending HR requests, completed approved leave this month, and rejected requests; a status distribution visualization; an upcoming approved leave table/card list; compact remaining-balance cards for the logged-in employee; status badges; and quick links to submit a request, open My Leave Requests, Manager Review Queue, HR Processing Queue, and Approved Leave Calendar. Data displayed should adapt to the logged-in profile/available records so employees see personal metrics, managers see assigned-team metrics, and HR sees organization-wide metrics. Use no external JavaScript integration. Create the main Pages/Leave_Dashboard.ds page stub if required by the page layout convention, while keeping all page segment files under the declared Pages/Leave_Dashboard/ scope or escalating the main stub if scope enforcement requires it.

## Permissions

Apply complete form, field, report, workflow-action, and dashboard access for Employees, Managers, and HR.

Edit the Employee, Manager, and HR profile files to add complete ModulePermissions, FieldPermissions, ReportPermissions, page permissions, and blueprint transition/button permissions for every implemented component. Employee: create Leave_Requests, view own requests and own balances, view dashboard/calendar as appropriate; cannot manage directory/types/balances/audit, cannot edit status, assigned manager, calculations, approval, HR, or balance snapshot fields. Manager: read employee directory and team balances, view assigned review queue/team-relevant calendar/dashboard, submit own leave, execute Approve/Reject only on requests assigned to their employee record; cannot process HR completion or directly edit protected fields. HR: full CRUD for Employees, Leave_Types, Leave_Balances, broad read of requests, execute Confirm Balance Update, view all reports/dashboard/audit; direct editing of workflow-controlled request status and audit snapshots should remain restricted where profile syntax permits. Audit_Log has read-only report access for HR and no user-facing add/edit/delete. Include every form field and every report produced by the approved plan. Do not create roles.
